# Reusable TV OS feasibility and evidence workflow

Documentation snapshot: 2026-11-08 04:48 Atlantic/Reykjavik. This workflow reproduced research/acquisition/documentation, NOT a successful TV OS replacement. Keep unit facts under `tvs/<tv>/evidence/`, generic procedure here. No Git repository is required: plain files, timestamped records, checksums and whole-file review packages work. Source control can be chosen for later coding, not assumed as a prerequisite to research.

## 1. Establish goal, scope and identity
Record internal OS replacement versus partial-stack userspace replacement versus launcher/app; never silently substitute an external HDMI computer. Record essential capabilities: panel/backlight, normal protected HDMI input, audio, remote/CEC, power/thermal; apps may be expendable but that does not waive display survival.
Use the new unit's official manual for normal information menus and existing lawful readbacks. For the present LG webOS6 family the verified manual routes were General > Devices > TV Management > TV Information and Support > Software Update VIEW ONLY; these routes are not universal across vendors/versions. Separate base model, regional suffix, firmware/build, board assembly/PCB revision, SoC and panel. Mark unavailable facts unknown; retain source/time/confidence. A seller part number or product-year processor description is not installed-chip proof. Do not ask repeatedly for identical evidence; invalidate affected facts when firmware/board/panel/source association changes.

## 2. Search for a legitimate target and independent recovery early
Review existing notes first. Bound new searches and record exact scope, URLs, quotes and limitations. Prefer manufacturer/exact-target maintained documentation; public community claims are leads until checked. Distinguish stock updates, ordinary reset, app development, root/homebrew and true custom-OS acceptance. Document boot/recovery entry, accepted artifact class, failure coverage, stock-restore applicability and early diagnostics. Do not infer boot policy from model year. No documented route in a bounded pass means dated deployment-no-go under current evidence, not impossible forever. Approved source learning can still finish after that no-go.

## 3. Acquire public source without treating availability as completeness
Find the manufacturer's normal public catalogUI; record exact query/model, release identifier, label, visible filenames, screenshot/context and timestamps. Do not invent download endpoints or copy privileged signatures. Download via ordinary publicUI; retain originals unchanged. Record regular-file status, filesystem bytes, local streaming SHA256 and whether the browser completed. UI omissions stay omissions. No vendor checksum means no authenticity claim. Local file hashes do not prove valid gzip/tar structures or source completeness.
Treat license notices as component-search leads only. Attribution labels, BSP packagegroups, kernel-package versions and RTK names do not prove hardware identity or a complete driver stack. Keep the notice inventory separate from the archive member/source inventory. A date-looking filename is not a verified release date.

## 4. Demonstrate bounded inspection before any originals
Use existing maintained utilities only when they actually enforce the required contract. If not, stop and obtain the scoped tooling phase; do not run an unguarded listing to discover what is inside. Define invocation-wide—not silently per-archive—member/pathname/metadata/expanded budgets, per-selected-text limit, wall/address-space controls and disk reserve.
