# Independent review: LG65NANO756PR native OS design and plan

**Verdict:** The plan is honest about the boot and recovery blockers. Its main defects are a few framing, ordering and boundary choices that could lead someone to treat it as more executable or more feasible than the evidence allows. Phase E (evidence only) can be approved separately from any future deployment, but only after the edits in §4.

## 1. Prioritized blockers

**P1. The header says "execute", the body says "plan only".**
- The `superpowers:subagent-driven-development / executing-plans … implement task-by-task` header, the title "Implementation Plan" and the checkbox tasks all invite an agent to start working.
- Task 1 steps 2 and 4 involve the TV, and Task 2 downloads archives. Global Constraints forbid both in this phase.
- An executor that follows the header would break the safety boundary.

**P2. Architecture A's boundary is undefined where it matters.**
- The supplied notice leads include components named like userspace services: `videooutputd`, `audiooutputd`, `omx-il-rtk`. If hardware control (picture, HDMI-in, audio routing) lives in vendor userspace, then "keep the vendor kernel, replace userspace" leads to one of two outcomes:
  - (a) panel, HDMI and audio stop working, so A fails first acceptance; or
  - (b) those vendor userspace binaries are kept, which moves toward the excluded "stock webOS plus launcher".
- No criterion defines how much vendor userspace can be kept before it stops counting as a replacement.

**P3. Recommending A assumes a boot advantage nobody has shown.**
- A needs the boot chain to accept a different root filesystem. B needs it to accept a different kernel.
- No evidence shows that either is easier, so "A is the first hypothesis" is an unsupported assumption.

**P4. The tasks are ordered so the most expensive work can be wasted.**
- Tasks 2 and 3 (downloading and auditing the source) come before Task 4 (boot route and recovery).
- The design already says no custom boot or recovery route is verified. If G3 fails, which is a likely outcome, all G2 work is wasted for the deployment goal.
- Nothing requires a cheap desk-only boot/recovery check first, and nothing defines "deployment no-go" as an acceptable way to finish.

**P5. Recovery proof has no workable path.**
- Task 4 needs validation on "an exact compatible development target or approved non-destructive route".
- In practice that means a matched spare board or TV, which needs purchase and hardware-access approval, or manufacturer recovery documentation. "Non-destructive route" is never defined.
- These other dependencies are also missing:
  - a legitimately obtainable stock image that the recovery path can restore;
  - an authorized diagnostic or log channel. M2 needs one, serial access is excluded, and if the display is lost nothing can be observed.

**P6. Under B or C, HDCP acceptance may be impossible, and the plan has no rule for that.**
- "Normal licensed HDCP" depends on the unit's own provisioning and on vendor components the owner may run.
- Whether licensed HDCP still works after the OS is modified is an unresolved rights and technical question. The plan treats it as a test result (V04), not as a gate for choosing an architecture.
- There is no explicit rule that a picture without HDCP is a failure.

**P7. Dependencies on chips outside the main processor are missing.**
- Standby and wake, the panel timing controller (TCON) and panel firmware, the HDMI receiver, the Magic Remote radio and pairing, Wi-Fi/Bluetooth firmware, and unit-unique picture/calibration data are not inventoried as separate dependencies.
- Radio regulatory constraints (running certified firmware and configuration unchanged, or turning the radios off) are absent.

**P8. The identity evidence is already inconsistent and nobody has flagged it.**
- S2 cites `65NANO756PR.AEK`. S4 cites `65NANO756PR.AEU`.
- Any mapping keyed to the suffix (U2, board candidates) is unreliable until U1 is resolved.
- If the firmware version changes later (for example through an update), G1–G3 evidence goes stale, and there is no rule to re-verify it.

**P9. Phase E is a bundle, and it drifts in scope.**
- It combines custom tooling code (which needs an addendum), downloads, read-only inspection and TV observation.
- Task 1 step 4 (playback, audio path, volume and power behaviour) goes beyond the "TV-information observation" Phase E describes. It involves pressing buttons on the TV.
- Other drift: "Cursor coding" names a specific tool, and there is no rule for a source release that is only available on request.

**P10. The baseline acceptance criterion is a category error.**
- The Filmmaker settings (panel 40, contrast 80, and so on) describe the vendor's picture-processing pipeline. A replacement OS has no equivalent.
- V02 does not say whether matching picture quality is required, out of scope, or measured with an instrument.

## 2. A, B and C as they should be split

| Branch | What is actually kept | Hidden dependency | Status |
|---|---|---|---|
| **A-K** | Vendor kernel and modules only | Hardware control must be kernel-side. If it is in userspace, first acceptance fails | Unverified |
| **A-H** | Vendor kernel plus vendor userspace hardware services; new init, system manager and UI | Needs an owner-set line between this and "stock plus launcher" | Partial-stack replacement; most at risk of drifting in scope |
| **B-same** | Same kernel version and config rebuilt from released source, so binary modules still load | Exact config, toolchain and module ABI match | Real kernel replacement in name; feasibility depends on the boot route |
| **B-new** | Newer kernel | Binary vendor modules unusable, so in effect C for those drivers | Should be labelled as close to C |
| **C** | Nothing from the vendor | Public documentation for the HDMI receiver, panel and power path | Unsupported |

The kernel label in the notice (4.4.84-711.kalaupapa.4) is only a label. If confirmed, it would make the B-same/B-new distinction decisive.

## 3. Acceptance gaps

- **Remote:** no minimum defined (basic IR vs Magic Remote pointer and pairing).
- **Audio:** no required route (internal speakers vs ARC/eARC/optical), even though Task 1 records it.
- **Security:** a networked replacement OS has no requirement for exposed services or security updates.
- **Reliability:** V08/V09 counts are placeholders. "Reliable display" has no definition the owner has signed.
- **No-go:** there is no final "deployment no-go" exit with a defined evidence report.

## 4. Exact plan edits

1. **Header and title.** Replace the superpowers header with:
   > "STATUS: Discovery plan. Only Phase E items listed under Approval are executable, after written owner approval. Tasks 3–5, M1–M7 and V01–V11 are requirements, not instructions. Do not run executing-plans or subagent-driven-development beyond Phase E."

   Rename the title to "Native TV OS — Discovery and Gated Requirements Plan".
2. **Architecture section.** Replace A/B with A-K, A-H, B-same, B-new and C as in §2. Add a decision U8a that the owner answers now, with no evidence needed: "Which vendor userspace components may be kept while the result still counts as replacement? Keeping stock init, system manager, compositor or app framework = excluded."
3. **Design table.** Change A's decision to "Hypothesis only; boot-route difficulty relative to B unknown."
4. **Order and registry.**
   - Add **Task 1.5 / U0, desk-only boot and recovery check**: public manufacturer documentation only, no TV interaction.
   - Run it before Tasks 2 and 3.
   - Add: "If no documented route is found, the owner decides whether evidence work continues for its own value. Deployment no-go is an acceptable final outcome."
5. **U1.** Add: "Supplied sources conflict (.AEK in S2, .AEU in S4). U2 is blocked until U1 is resolved. Any version change invalidates G1–G3 evidence and requires re-verification. Do not change the auto-update setting; record it if visible."
6. **Task 1.**
   - Split into **1a**: an owner-performed TV-information readout, in Phase E.
   - And **1b**: a playback/audio/remote/CEC baseline, owner-operated, with no automation and its own approval.
   - Add: "Service documentation must come from a lawful source."
7. **Task 2.**
   - Add a policy for nested archives (recursion depth, total expanded size).
   - Add: "If source is only available on request, stop and ask the owner; an inquiry needs approval. This is not a failure."
8. **Task 3 and U5.** Add an inventory of chips and data outside the main processor:
   - standby/power controller;
   - TCON and panel;
   - HDMI receiver;
   - remote radio and Bluetooth;
   - Wi-Fi;
   - unit-unique picture/calibration data;
   - HDCP provisioning access path;
   - radio regulatory constraint.
9. **New gate before G4, HDCP rights and function.**
   > "If an architecture cannot use the unit's own HDCP provisioning through components the owner may lawfully run, that architecture fails first acceptance. No pass without HDCP."
10. **Task 4.**
    > "Recovery validation needs (i) a matched spare unit or board tied to G1/U2 (purchase and hardware-access approvals), or (ii) manufacturer-documented recovery. Otherwise G3 = FAIL, which ends deployment."

    Add as G3 requirements: a legitimately obtainable stock restore image, and an authorized diagnostic/log channel.
11. **V02.**
    > "Acceptance = stable, correct-range SDR picture. Picture-quality parity with the vendor's Filmmaker mode is out of scope unless separately specified with a named measurement instrument."
12. **M4/M7.** Add a network-security requirement: minimal exposed services, an update policy, and network off by default if unsupported.
13. **Self-review status line.** Replace with "PHASE E APPROVAL CANDIDATE — NOT IMPLEMENTATION-READY, NOT FLASH-READY."

## 5. Can Phase E be approved separately?

**Yes, with conditions.** The approval text must:

- list exactly what is allowed:
  - **E1:** public download, hashing and archive-member listing with a maintained archive reader;
  - **E2:** custom tooling, only under a reviewed test-first addendum;
  - **E3:** the owner-performed Task 1a readout;
  - **E4:** the desk-only boot and recovery check.
- exclude Task 1b, any TV commands, inquiries and purchases;
- state that it creates no commitment or presumption toward Phase B or T;
- define a standalone deliverable (identity record, source inventory, U0 finding) that has value even if deployment never happens.

Without edits 1, 4 and 6, the approval is not cleanly separable, because the current wording carries momentum toward execution.
