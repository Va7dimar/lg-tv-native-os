# LG 65NANO756PR — independent planning review (read-only)

Scope: desk review only. I did not touch the TV, network, or credentials. This ranks routes toward a *custom/native OS experience* while preserving panel, HDMI input, audio, and power, given a rooted unit (root SSH, Homebrew 0.7.3) on signed production firmware.

## Top-line verification first (do this before ranking debates)

The single most decision-relevant unknown is **whether the stock display path can be driven by a non-vendor process at all**. Everything below forks on it. The highest-value next read-only step is characterizing the compositor/DRM relationship, not more boot forensics. Secondary: confirm the writable-storage execution surface you actually get as root.

## Disagreements / corrections to current evidence

1. **"1.07/2.03GB storage" vs "~7.3 GiB eMMC."** The TV Information figure is the *user/app* partition free space, not the disk. The live inventory's eMMC size is right; keep the plan from conflating them. Your custom userland budget is whatever is free on `p58`/`p59` + `/media/developer`, not 2 GB.
2. **A/B banks ≠ recovery.** The inventory already flags this, but the native-OS *design* doc still leans on "A/B redundancy is a genuine recovery signal." It is a redundancy *signal*, not a proven recovery route: you have not shown the bootloader will fail over, nor that you can write the standby bank and select it. Treat it as unproven until bank-select logic is found.
3. **`secured`/`prodkey` is correctly read as "likely signed boot," but the plan sometimes treats it as proven secure-boot enforcement.** Metadata naming is not proof the bootloader *rejects* unsigned kernels. It is the right default assumption (plan for enforcement), but label it inference, and note the cheap disproof: the gcc/kernel-version match between on-TV and the OSS drop is not evidence either way about signature checks.
4. **Mali DRM existence ≠ usable accelerated display.** The design doc's HDMI-RX/scaler/audio capability list is sourced from *source-tree filenames*, not from a working userspace API. Do not let "driver file exists" become "capability available."

## Ranked routes

### Route 1 — Fullscreen custom shell retaining vendor kernel/services/compositor (RECOMMENDED FIRST)
**Delivered capability:** a custom root-launched UI/app that owns the screen at boot (your own launcher, dashboard, or an AppleTV-first "appliance" face), while the vendor kernel, tvservice, audio, HDMI-input switching, and power/thermal stay stock and untouched. This is the only route that preserves *all four* must-keeps by construction, because it writes nothing to system partitions.

**Why first:** zero writes to kernel/rootfs/boot. Fully reversible (remove the Homebrew startup hook). It is the honest floor of "custom OS experience" and the platform every other route builds on.

**Evidence needed:** (a) a Homebrew/startup hook that launches your process at boot and survives reboot; (b) proof you can present fullscreen *over or instead of* the stock launcher without stopping the compositor; (c) that HDMI-input selection and audio route remain controllable (via existing luna/SSAP services) from your shell.

**Next read-only TV commands (owner-noticed, read-only):**
- `ls -la /media/developer /var/lib/webosbrew /home/root` — confirm writable exec surface and existing hook dir.
- `cat /var/run/nyx/os_info.json` is already captured; instead enumerate the service bus surface read-only: `luna-send -n 1 -f luna://com.webos.service.applicationmanager/listApps '{}'` (lists apps; no state change) — confirms you can drive app/launcher from CLI.
- `ps -ww | grep -iE 'surface|compositor|luna|sam|webappmgr'` — identify the compositor and app-manager process names (no identifiers).
- `cat /proc/<compositor_pid>/maps | grep -i -E 'wayland|gbm|mali'` — does the compositor own the Wayland/GBM device.

**Risks/reversibility:** low. Main risk is a startup hook that wedges boot UI; mitigate by never disabling the stock launcher in v1 — launch *alongside*, then layer on top. Fully reversible.

**Go/no-go gate:** GO already — this needs no boot/flash. First non-read-only action (installing a startup hook) is the first thing needing owner notice.

### Route 2 — Alternative Linux userland / chroot drawing via the stock compositor or DRM/fbdev
**Delivered capability:** a full secondary Linux userland (Debian/Alpine armhf) in a chroot/container on writable storage, giving you a real package ecosystem and custom services, rendering either (a) through the stock Wayland compositor as a client, or (b) directly to `/dev/fb0`/`/dev/dri/card0` if the compositor can be yielded.

**Evidence needed:** the pivotal one — **can a non-vendor client reach the display?** Two sub-cases: Wayland-client (needs the compositor's socket + protocol compatibility; preserves everything) vs. direct DRM/fbdev (needs the compositor to release the device — higher risk to "preserve panel/HDMI"). armhf userland must match the 32-bit ABI (confirmed armv7l).

**Next read-only TV commands:**
- `ls -la /run/*/wayland-* /tmp/*wayland* 2>/dev/null; env | grep -i wayland` (run in a root shell context) — is there a reachable Wayland socket.
- `ls -la /dev/dri /dev/fb*; cat /sys/class/drm/card0*/status` — DRM connectors/framebuffer presence (no writes).
- `fuser /dev/dri/card0 /dev/fb0 2>/dev/null` or `ls -l /proc/*/fd | grep -E 'card0|fb0'` — which process holds the display device (determines whether direct-render is even possible without evicting the compositor).
- `cat /proc/cpuinfo | grep -i features; getconf GNU_LIBC_VERSION` — ABI/libc target for the chroot.

**Risks/reversibility:** chroot itself is reversible (it's a directory). The risk concentrates in display method: Wayland-client = low; direct DRM/fbdev while compositor runs = potential blank screen / needs reboot to recover (recoverable, but a live-use regression). Never the direct path until Route-1 telemetry shows who owns `card0`.

**Go/no-go gate:** GO for the chroot + Wayland-client experiment (no system writes). NO-GO on direct DRM takeover until device-ownership is mapped and a tested "reboot restores stock" is demonstrated.

### Route 3 — Compositor replacement (stock compositor stopped, yours substituted)
**Delivered capability:** your own compositor/UI owning the panel directly — much closer to "native OS feel," retaining only the vendor kernel + Mali/display drivers.

**Evidence needed, all currently missing:** (a) a clean, scripted stop of the stock compositor *and services that depend on it* without tripping a watchdog that reboots or powers down; (b) proven restoration on reboot (stock comes back untouched because you wrote nothing permanent); (c) Mali/GBM/DRM usable by your compositor with the vendor kernel's exact driver ABI; (d) HDMI-input and audio services survive or are re-startable.

**Risks/reversibility:** medium. Because you write nothing to system partitions, a bad run should recover on power-cycle — *but only if no watchdog escalates to a persistent fault state*. The "preserve HDMI/audio/power" requirement is genuinely at stake here: these are tied to vendor services that may assume the stock compositor.

**Go/no-go gate:** NO-GO until Route 1+2 have mapped (i) device ownership, (ii) the watchdog/thermal daemons and their triggers, (iii) a demonstrated stop→reboot→stock-restored cycle with owner present. Every run is a live, owner-noticed session with the owner watching the screen.

### Route 4 — Custom boot / custom kernel (LAST)
**Delivered capability:** the only route that is "native OS" in the strict sense (replace kernel/init). Also the only one that can hard-brick.

**Evidence needed before it is even designable:** (1) characterized bootloader signature policy — is an unsigned/self-signed kernel actually rejected; (2) a bank-select mechanism you can drive; (3) an **independent recovery channel** that works when the replaced system won't boot (serial console / USB recovery / factory loader) — none identified in any evidence file to date; (4) legal, usable firmware blobs for Mali/HDMI/panel.

**Risks/reversibility:** potentially irreversible (brick). The whole corpus's recovery-case and boot-route docs correctly stand at NO-GO.

**Go/no-go gate:** HARD NO-GO. Gate is unchanged from recovery-case.md: a verified boot route **and** an independent, tested recovery **and** a specific owner decision. Do not write to kernel/rootfs/boot/tvservice/system partitions under any current evidence.

## Staged plan

**Stage A — Characterize the display/service surface (read-only, owner-noticed SSH session).** Run the Route-1 and Route-2 read-only commands above. Deliverable: a "display ownership + service map" evidence file — who holds `card0`/`fb0`, compositor process identity, Wayland socket reachability, watchdog/thermal daemon names, HDMI-input and audio service names. This single artifact decides whether Route 2/3 are live or dead. No identifiers captured.

**Stage B — Route 1 build (first non-read-only work; needs owner notice).** Install a startup hook that launches a fullscreen custom shell *alongside* the stock launcher. Verify reboot persistence, HDMI-input switching, audio, power/standby all still work from your shell. This delivers a real "custom OS experience" at zero brick risk and becomes the host for everything else.

**Stage C — Route 2 chroot (Wayland-client first).** Stand up an armhf userland on writable storage; render as a Wayland client if Stage A found a reachable socket. Defer direct DRM/fbdev.

**Stage D — gated.** Route 3 only after Stage A maps the watchdog and a stop→reboot→restore cycle is demonstrated with owner present. Route 4 stays blocked pending the recovery/boot gates that remain unmet.

**Invariant across all stages:** no writes to kernel/rootfs/tvservice/boot/system partitions; every non-read-only TV action is owner-noticed; boot/flash needs verified route + independent recovery + explicit owner decision; no serial/nduid/MAC/credentials committed.
